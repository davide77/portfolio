# {{PROJECT_NAME}} - project instructions

## Brand: single source of truth is `brand.md`

The {{PROJECT_NAME}} brand (positioning, voice, colours, typography, logo, photography direction) is defined in **[brand.md](brand.md)** at the repo root. Everything else (SCSS tokens, JSX components, copy) is derived from it.

**Always read [brand.md](brand.md) before:**

- writing copy (page content, metadata, alt text, emails, social posts, PR descriptions, commit messages that ship user-facing text).
- generating any visual asset (images, OG cards, posters, slide decks, PDFs, banners).
- introducing or changing a colour, font, or layout primitive.
- auditing existing copy or visuals for brand consistency.

### Where the brand lives in this repo

- [brand.md](brand.md) - narrative source of truth. Update here first.
- [src/styles/abstracts/_colors.scss](src/styles/abstracts/_colors.scss) - colour map. Mirrors `brand.md`. Keep in sync.
- [src/styles/abstracts/_typography.scss](src/styles/abstracts/_typography.scss) - font stacks and size/weight/line-height scales.
- [.claude/skills/brand-guidelines/SKILL.md](.claude/skills/brand-guidelines/SKILL.md) - the skill Claude invokes when styling an artifact. Defers to `brand.md`.
- [.claude/skills/brand-voice/SKILL.md](.claude/skills/brand-voice/SKILL.md) - the skill Claude invokes when writing or auditing copy. Defers to `brand.md`.

If work needs to deviate from the brand, stop and flag it before shipping.

## SCSS architecture: single source of truth is `scss-utility-architecture`

The project's SCSS layer (token maps, accessors, generated utilities, BEM components, container-query-first responsive behaviour) is defined in **[.claude/skills/scss-utility-architecture/SKILL.md](.claude/skills/scss-utility-architecture/SKILL.md)**. That skill is the conventions document for every style change.

**Always invoke the `scss-utility-architecture` skill before:**

- adding or editing any `.scss` / `.module.scss` file.
- adding or removing a colour, spacer, font size/weight, line-height, breakpoint, radius, or z-index token.
- generating new utility classes or extending an existing utility family.
- creating a new component's sibling `.module.scss`.
- writing responsive behaviour (container queries vs viewport media queries).

### Non-negotiables enforced by the skill

- Token maps and accessors only: `color()`, `spacer()`, `font-size()`, `font-weight()`, `line-height()`, `bp()`, `z()`. No raw hex, no raw px outside the scale.
- `abstracts/` emits zero CSS. Maps, functions, mixins only.
- Utility classes are generated by `@each` loops over token maps. Adding a new utility family means extending the map first, then the loop.
- Reusable components respond to their container (`@container`, `cqi`), not the viewport. Only page chrome uses `@include min(bp(...))`.
- Anything covered by an existing utility class belongs in JSX, not in component SCSS. See "Utility classes over component SCSS" below.

If a design value does not fit the existing scale, extend the map in `abstracts/` first, then reference it via the accessor. Never drop a raw literal into a component file.

## Commit messages: no AI co-author trailer

**Never add `Co-Authored-By: Claude ...` (or any AI attribution) to commit messages, PR bodies, or any git metadata.** The user is the sole author on record.

- When writing `git commit -m`, end the message body at the last meaningful line. Do not add a blank line followed by `Co-Authored-By:`.
- Same rule for `gh pr create --body` and any other place a commit-style trailer might be added.
- Use a plain HEREDOC with only the subject and body, nothing after.

### Why

The user does not want AI attribution in the git history or on GitHub. It makes the work look less personal and is unnecessary noise in the log.

## Writing style: no long dashes

**Never use em-dashes (`—`) or en-dashes (`–`) in any file you write or edit.** Regular hyphens (`-`) are fine and encouraged where appropriate.

This applies to:

- User-facing copy (JSX, strings, page content, metadata, alt text, SEO descriptions)
- Code comments (including JSDoc and inline)
- Commit messages and PR descriptions
- Documentation and markdown

### What to do instead

- **Parenthetical break:** use a hyphen with spaces around it: `The trial is free - come along before you decide.`
- **Numeric or price range:** use a plain hyphen: `£300-£400`, `9-11 year olds`, `Sept-Aug`. These are fine, it is only the long dashes that look AI-generated.
- **If in doubt:** rewrite the sentence so no dash is needed at all. Short, direct sentences read more human than long ones stitched together with dashes.

### Why

Em-dashes and en-dashes are a well-known "AI tell" and the site copy must read like it was written by a human, not a language model.

### Exception

Character classes inside regexes that intentionally match either a hyphen or an en-dash when scraping third-party HTML. Those are defensive parsing, not prose. Leave them alone.

### Before finishing any edit

Scan your new or modified content for `—` and `–` and replace them. Do not commit either character outside the regex exception above.

## Utility classes over component SCSS

When a style only expresses layout, spacing, alignment, text size/weight, or colour, **use the existing utility classes in JSX. Do not write new component SCSS for it.** Component SCSS is for genuinely component-specific concerns (borders, radii, backgrounds, transitions, custom dimensions, composed typography, pseudo-elements, positioning, responsive overrides).

### Where the utilities live

- [src/styles/utilities/_flex.scss](src/styles/utilities/_flex.scss) - flex display, direction, wrap, justify, align, `is-flex-1`, plus responsive `is-flex-{sm,md,lg}-*` variants.
- [src/styles/base/_base.scss](src/styles/base/_base.scss) - `has-gap-N`, `text-{xs..hero}`, `has-font-{weight}`, `leading-{name}`, `text-{left|center|right|justify}`, `uppercase`, `is-{colour}`, `bg-{colour}`, `has-border-{colour}`.
- [src/styles/base/_measures.scss](src/styles/base/_measures.scss) - `has-m*-N`, `has-p*-N` spacing utilities.
- [src/styles/base/_reset.scss](src/styles/base/_reset.scss) - already sets `ul, ol { list-style: none }` and `* { margin: 0; padding: 0; box-sizing: border-box }`. Do not redeclare these in component SCSS.

### Mapping

| SCSS declaration | Utility class |
| --- | --- |
| `display: flex` / `inline-flex` | `is-flex` / `is-inline-flex` |
| `flex-direction: column` / `row` | `is-flex-column` / `is-flex-row` |
| `flex-wrap: wrap` / `nowrap` | `is-flex-wrap` / `is-flex-nowrap` |
| `justify-content: center\|space-between\|flex-start\|flex-end\|space-around` | `is-justify-{center\|between\|start\|end\|around}` |
| `align-items: center\|flex-start\|flex-end\|stretch\|baseline` | `is-align-{center\|start\|end\|stretch\|baseline}` |
| `flex: 1` | `is-flex-1` |
| `gap: spacer(N)` | `has-gap-N` |
| `margin-*: spacer(N)` (top/right/bottom/left/x/y) | `has-m*-N` |
| `padding-*: spacer(N)` (top/right/bottom/left/x/y) | `has-p*-N` |
| `text-align: X` | `text-X` |
| `font-size: font-size(X)` | `text-X` |
| `font-weight: font-weight(X)` | `has-font-X` |
| `line-height: line-height(X)` | `leading-X` |
| `color: color(X)` | `is-X` |
| `background-color: color(X)` | `bg-X` |
| `border-color: color(X)` | `has-border-X` |

### Mixed rules

If a rule combines utility-covered declarations with component-specific ones, move only the utility-covered ones to JSX. Keep the rest in SCSS. Do not force a mixed rule into utilities-only by splitting across multiple elements.

### Do not convert

- Declarations inside `@media` / `@include min(...)` / `@include max(...)` blocks where no responsive utility covers the property.
- Pseudo-elements (`::before`, `::after`).
- Rules with `!important`.
- Button, form, modal, and topbar chrome internals - these are component compositions, not utility candidates.
- Values that are not in the token scale (e.g. `gap: 12px`, `margin: 3rem`) - fix the value or leave the rule alone, do not invent a new utility.

### Why

The project's SCSS layer is token-driven and generates a complete utility set at build time. Re-declaring `display: flex; flex-direction: column; gap: spacer(3)` in a BEM component file is dead weight: the same declarations already ship as `is-flex is-flex-column has-gap-3`. Writing utilities in JSX keeps component SCSS files small and focused on what is genuinely component-specific.

## No inline style props in JSX

**Do not use inline styles (`style={{ ... }}`) in JSX or TSX files.**

- Put layout, spacing, alignment, opacity, sizing, and text presentation into utility classes.
- If a needed utility does not exist yet, add it in the shared style layer and use a class.
- Component-specific visuals belong in component SCSS, not inline style objects.

### Allowed exceptions

- framer-motion driven values: `style={{ y: scrollY, padding, boxShadow }}` where those are `MotionValue`s or motion templates.
- Per-instance CSS custom properties: `style={{ "--card-bg": colorMap[bg] } as CSSProperties}` when the module SCSS reads `var(--card-bg)`.

### Why

Inline styles bypass the project's token system, reduce consistency, and make style auditing harder. Class-based styling keeps the codebase consistent, searchable, and token-driven.

## Tokens vs literals

- **Add a token** when the value is reused across 2+ components or represents a brand decision (a colour, a type-scale step, a standard radius).
- **Use a literal** for one-off component-specific values (e.g. an absolute-positioned sticker's `top: 80px`).

If you are tempted to hard-code a hex outside `_colors.scss`, stop and add it to the map first, and then check it is actually in the brand palette per [brand.md](brand.md).

## No hardcoded values in JSX: use `src/constants/`

**Components render data, they do not hold it.** Strings, lists, links, and config values live in [src/constants/](src/constants/), are imported, and rendered. Components must not have user-facing literals baked into the JSX.

### What must come from `src/constants/`

- **User-facing copy and strings** - headings, button labels, paragraphs, alt text, placeholders, SEO titles/descriptions, aria-labels. No inline literal strings in JSX that ship to the user.
- **Structured content / data arrays** - nav items, card lists, feature grids, FAQ entries, testimonials, pricing tiers, footer columns. Components iterate over imported data.
- **URLs, routes, and contact info** - internal route paths, external links, phone numbers, email addresses, social handles. Imported, never typed inline.
- **Numeric / config values** - thresholds, durations, counts, prices, breakpoint pixel values used in JS, animation timings (when not in SCSS), API limits. No magic numbers in components.

### File layout

- Location: [src/constants/](src/constants/) - top-level folder, one file per domain.
- Naming: kebab-case filenames, camelCase or SCREAMING_SNAKE_CASE exports.
- Suggested split: `site.ts` (brand name, tagline, contact, socials), `nav.ts` (top + footer nav), `routes.ts` (internal route paths), `content/<page>.ts` (page-specific copy and data arrays), `config.ts` (numeric thresholds, durations, limits).
- Use TypeScript: type each export so consumers get autocomplete and refactors are safe.

### Pattern

```tsx
// src/constants/nav.ts
export const PRIMARY_NAV = [
  { label: "About", href: "/about" },
  { label: "Work", href: "/work" },
  { label: "Contact", href: "/contact" },
] as const;

// src/components/TopNav.tsx
import { PRIMARY_NAV } from "@/constants/nav";

export function TopNav() {
  return (
    <nav>
      {PRIMARY_NAV.map((item) => (
        <a key={item.href} href={item.href}>{item.label}</a>
      ))}
    </nav>
  );
}
```

### Allowed exceptions

- Structural / non-content strings that are part of the markup contract: `aria-hidden="true"`, `role="presentation"`, `type="button"`, `data-*` attribute values used by CSS or tests.
- `className` strings - utility class names belong inline in JSX.
- One-off purely visual literals with no semantic meaning (e.g. an SVG `viewBox`, a `tabIndex` of `-1`).
- Test fixture data inside `*.test.ts(x)` files.

If you find yourself typing a literal string or number that a user could read or that controls behaviour, stop and move it to `src/constants/` first.

### Why

Constants files give the brand voice and content a single audit surface, make i18n possible later, prevent copy drift between similar components, and stop magic numbers from hiding behavior in render code. Components stay focused on layout and interaction; content stays where it can be reviewed against [brand.md](brand.md).

## TSX patterns

- Use `cx(...)` from [src/components/cx.ts](src/components/cx.ts) for conditional `className` composition.
- Default to Server Components. Add `"use client"` only when a component needs framer-motion, state, effects, or browser APIs.
- Component file convention: every component has a sibling `.module.scss` file. Class names inside the module use camelCase (CSS Modules best practice); BEM semantics with double-underscore can be used where useful (e.g. `card__title`).
